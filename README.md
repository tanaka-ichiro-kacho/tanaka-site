# 月刊・田中課長 ― 収益化パイプライン設計書

## 前提として理解しておくこと
収益を保証する設計は存在しない。ここでの目標は「収益が出る確率を最大化し、
無駄な実装コスト(今は使えないAPIへの依存など)を避けること」。

## フェーズ1: 手動データ + 半自動生成(今日から開始できる)

理由: Amazon Product Advertising API / Creators APIは、直近30日間で一定件数
(2025年11月の規約変更以降は10件)の売上実績がないと利用できない。
このサイトはまだ売上実績ゼロなので、API連携から作り始めると必ず詰まる。

構成:
1. `products/products.json` … SiteStripeで手動取得したアフィリエイトリンクを登録
2. `prompts/article-generator-prompt.md` … Claude Codeで記事を生成する際のプロンプト
3. 生成した記事は **必ず人間が最終チェック** してから公開(全自動公開はしない)
4. 静的サイトジェネレータ(Next.js推奨。ホスティングはVercel無料枠でOK)でビルド

### Claude Codeでの具体的な作業手順
1. products.jsonにSiteStripeで取得したリンクを3〜5件登録する
2. article-generator-prompt.mdを使って記事を1本生成 → 人間がチェック → index.htmlのカード
   ・記事詳細ページとして追加するコンポーネントを作る(既存のプロトタイプのCSSトークンを流用)
3. 週1〜2本のペースで公開。量より「型の再現性」を優先する
4. Google Search Consoleにサイトを登録し、インデックス状況とクエリを毎週確認

## フェーズ2: 計測ループ(記事が10本を超えたら)

- Google Search Console: どの記事がどんな検索語で表示されているか確認
- Amazonアソシエイト管理画面のレポート: どのリンクがクリックされ、購入に至っているか確認
- CTRが低い記事 → 商品紹介の接続が唐突になっていないか見直す
- 表示回数はあるがクリックが少ない記事 → タイトル・導入文を見直す

## フェーズ3: API連携への移行(直近30日で10件の売上を継続的に達成できたら)

- Amazon Creators API(PA-APIの後継)への申請・移行を検討
- 価格・在庫の自動更新、商品画像の自動取得が可能になる
- ただしこの時点でも「記事の自動全公開」はしない。生成の効率化であって、
  人間のチェック工程は外さない(Googleのスパムポリシー対策として)

## 絶対に守ること(景表法・スパムポリシー対策)
- 広告を含む記事には必ず「PR」表記(プロトタイプで実装済みのpr-badgeを流用)
- 本文に断定的な効能表現を書かない
- 同一エピソードの使い回しをしない(past_articles_summaryで管理)
- 記事は生成→人間チェック→公開の順を必ず踏む
